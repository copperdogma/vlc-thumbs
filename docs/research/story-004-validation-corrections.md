## Background cache pollution follow-up

A stronger locally demonstrated quota case places the cold entry just newer than the last RAM hover. Timestamp recency alone still evicts the hovered payload and loses restart reuse. [RocksDB block-cache documentation](https://github.com/facebook/rocksdb/wiki/Block-Cache) explains higher/lower priority retention pools for valuable entries competing with ordinary data. We adapted only that priority-pool idea to demand-used thumbnail files versus background/prepared files; no RocksDB dependency or code was introduced. Bound priority state to the selected identity's 512 sample records, clear it on identity changes/removal, and retain the 256 MiB hard eviction bound. Touch or explicit `allowEviction:YES` store promotes demand; passive enumeration does not. Priority is a session-local retention preference, not permanently pinned user data. The fresh demand/current manifest tier remains evictable under the hard cap. The 3,410-check baseline/corrected comparison above covers older/newer cold pressure, newly decoded demand, restart reuse and capacity cleanup; the 235648 artifacts remain intermediate.
